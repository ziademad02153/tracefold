# M2 / M3 — Repository environments and existing tests

> Historical record. For authoritative documentation use [the documentation index](../../README.md). Commands and conclusions below reflect the recorded stage; use the current development guide for execution.

4 November 2026. Implemented local supported-profile pilot. No repository-wide generation, extra language provider, coverage dashboard, accounts or notifications were added.

The consolidated [M3 Validation Report](m3-report.md) distinguishes existing-test execution from AI file generation and records the company validation as NOT RUN. The upstream success is not company acceptance.

## What the user can do

Add a public GitHub repository -> Open project -> Repository tests -> Inspect a branch/tag/commit and component root -> select the Python execution profile, dependency files/packages, install mode and approved plugins -> save the exact configuration -> review and approve preparation -> run existing tests -> inspect per-case evidence -> rerun using the same snapshot/environment -> reopen saved reports.

No Gemma connection is required. Install/test setup is explicit configuration, not inferred by the model. Separate projects within a monorepo need separate component profiles. This is supported Python project execution, not automatic support for every Python repository.

## Environment and source handling

- Resolve a ref to a commit before inspection. Retain the complete bounded archive, including package initialization, resources, conftest and configuration. Validate paths, symlinks, collisions and sizes. Rehash cached content against the original snapshot identity before use.
- Cache snapshots under ignored .tracefold/snapshots on the project drive. A verified directory is published through an atomic metadata-file replacement. Windows folder-rename failure was found and resolved without exposing a partial snapshot.
- Discovery reports src/flat layout, installability, declared runtime, build requirements, available dependency files, pytest config files and extras. It does not execute repository code in the API process.
- The selected manifests/packages are normalized and hashed. Registry requirement specifications are supported; direct URLs, VCS paths, nested requirements options and unsupported lock adapters are rejected explicitly.
- A source-free downloader fetches wheels from the configured public registry index using a bounded tmpfs staging area. No repository code or application credentials are mounted in the networked downloader.
- Project installation runs offline inside an isolated container. A fresh virtual environment receives the wheels, build requirements and real project installation. Pip checks dependency compatibility. Python package build hooks run inside that container, never on the host.
- Freeze the resulting environment as an immutable Docker image ID. Record installed distribution versions, interpreter/platform, wheel hashes and manifest identities. The native evidence executor and preparation script hashes are recorded; the executor itself is pinned in the image.
- Preserve pytest configuration and conftest/fixtures; disable automatic third-party plugin loading and load explicitly approved plugin import names. The user's test selection is a recorded argument array. Platform-controlled evidence/collection overrides are explicit.
- Collection and execution run in fresh ephemeral copies under the same prepared image. Preserve full native node IDs including classes and parameterization. Compare the two inventories before accepting outcomes.
- Run with no network, non-root user, read-only root/input, dropped capabilities, bounded CPU/memory/processes/time/output and temporary writable space. Logs and native evidence are returned with checksums. Preparation has a total deadline; timeouts remove the named container as well as its CLI.
- Zero tests, unmatched/duplicate evidence and unknown outcomes cannot pass. Show fixture/teardown errors, skips, expected failures and unexpected passes separately. Rebuilding an environment preserves earlier run environment manifests.

## Limits and release decision

Only the Python 3.11/Linux/pip/pytest profile is installed. Dependency wheels must be available; no automatic uv/Poetry lock interpretation, private registries, separately packaged workspace dependency ordering, external services, GPU environments, additional Python runtime versions or non-Python runtime is promised. Dynamic dependency/build needs must be supplied explicitly and may fail offline preparation. Source-path mode is an explicit choice for uninstalled projects, not an implicit sys.path repair.

Initial limits include 16 MB compressed source, 64 MB expanded source, 5000 files/cases, 8 MB per source file, 1 GB container memory, 256 MB temporary working space, 360 seconds total preparation, 120 seconds for collection plus execution and bounded output/artifacts. Large packages/data sets can exceed these limits and are unsupported by this profile.

This remains a supervised single-user local pilot. Authentication, job queue/recovery, shared concurrency control, private credentials, artifact retention/backups, image/cache garbage collection and preparation-container disk quotas require the operational release gate before a shared untrusted workload service. Prepared images/snapshots are retained locally; they are not exported to GitHub with the source code. Evidence artifacts are currently bounded inline text, not a complete binary artifact store.

M2/M3 technical behavior is demonstrated on the supported upstream profile. Acceptance of the user's actual company repository remains pending its URL and install/test commands.
