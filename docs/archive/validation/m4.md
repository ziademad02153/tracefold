# M4 — Repository-context test generation

> Historical record. For authoritative documentation use [the documentation index](../../README.md). Commands and conclusions below reflect the recorded stage; use the current development guide for execution.

Implementation and local validation: 4 November 2026. Scope: the existing supported Python 3.11/Linux/pip/pytest provider. This is a bounded repository testing workflow, not automatic exhaustive testing of every module.

## User workflow

1. Add a public GitHub repository and open its Project → Tests → Existing tests.
2. Inspect a revision/component, review installation inputs, save and approve environment preparation.
3. Run existing tests. Keep baseline failures visible; they are not automatically attributed to generated tests.
4. Open Generated tests or scroll to generation in the prepared execution profile. Select up to three source modules and describe required outputs, boundaries and exceptions.
5. Gemma receives full bounded selected modules, one-hop internal import context, relevant bounded examples/fixtures and installed package metadata. Source is treated as untrusted data. No source code is executed on the API host for discovery.
6. Review the saved draft's scenarios, real project imports, assertions and source code. Edit if necessary and save the reviewed draft. Approval is disabled while edits are unsaved.
7. Approve the exact saved suite hash. Approved files are immutable. Generation does not modify or commit production files.
8. Run existing + approved tests. Native per-case results distinguish existing and generated provenance. Collection/setup errors and missing evidence block a clean success.
9. After committing a repair, enter its revision using Open repaired revision. Review and prepare that new profile. Select the same approved suite and run it unchanged.
10. Reopen the saved report in Runs. It retains source/profile/environment identities and compares generated outcomes; changed environments and existing inventory changes are explicit.

A repository without existing tests can start at generation after preparation. Its existing-test phase is explicitly empty; success refers to the generated cases only. Environment/import/collection errors are not treated as an empty valid baseline.

## Execution and approval contracts

- Suites have independent IDs and SHA256 definitions: provider/version, origin profile/source, request, generated files and generation metadata. Editing creates a new hash and invalidates stale approval.
- Core persists suites, approvals and runs without importing Python/pytest. SuiteProvider is an optional capability extension; other execution providers need not implement generation.
- Python-specific options and generation forms live behind the provider/view registry.
- Prepared environments pin their executor script and record suite_execution_version=1. Old M3 environments require an explicit rebuild before generated overlays; old reports retain original manifests.
- Test files use a reserved path; overlays cannot overwrite a repository file. Only isolated writable copies receive approved additions. Source and controls are mounted read-only.
- Existing and generated tests execute in separate fresh source copies inside the same pinned environment. This is not a single combined pytest process; phase-specific configuration/arguments are retained. Existing CLI selection arguments apply to baseline tests; generated execution selects the approved file explicitly while retaining project configuration and fixtures.
- Runtime has no network, non-root execution, read-only root, dropped capabilities, CPU/memory/PID/time/output limits and bounded temporary storage. Project install hooks remain inside offline preparation isolation.
- Reusing a suite on another revision preserves its exact files/hash. A new revision needs a prepared environment for that source. The report identifies environment changes and does not claim a code-only controlled experiment when images differ.
- Structural checks are not a proof of test quality or a security sandbox. Expected behavior and assertion review remain the developer's responsibility.

## Current boundaries and next gate

Generation is one reserved pytest file per batch, 3–8 test functions, up to three selected modules, bounded source/context and two structural attempts. It is not a repository-wide scheduler or dependency graph resolver. Large modules/context, async/class-heavy APIs and complex fixtures can require a narrower request or an explicit unsupported result. Existing pytest parametrization can yield more native cases than function definitions.

The connector remains public-only. Supported dependency/runtime/service/workspace limits from M2_M3.md still apply. No coverage, accounts, dashboards, notifications, GitHub comments, extra models or other runtime providers were added.

The next acceptance gate is the real company repository and an as-built architecture review before any expansion. Shared daily deployment is a separate operational gate: authentication/access control, queued/cancellable jobs, aggregate quotas, preparation disk controls, migrations/backups and PostgreSQL validation remain open.
